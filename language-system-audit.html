Sixteen test suites pass. The system still fails the writer on more than half the dialogue in a real book. This report explains the gap, names the one line of code that causes most of it, and proposes what the app should become.

Audited 29 July 2026 Corpora Hollow Iris (122,795 w) · The Root Crown (111,836 w) Suites run 18 New harness scripts/ood-language-audit.ts

01 — Verdict

The engine is real. The wiring into it is broken.

Latent Write is not a gimmick. Underneath it is a genuine prose-analysis engine, roughly 400 KB of hand-written linguistic code with a real test culture around it. But on a manuscript it has not been hand-fed, it spends most of its time saying nothing, and the writer is never told that is what is happening.

52.9% of dialogue gets no speaker at all on a real 40-chapter manuscript, in the default mode, in the state the app actually ships in. Hollow Iris, 650 dialogue segments
0% of the main cast is found by the name extractor that feeds speech detection. Not one protagonist, in either novel. Iris, Nora, Mira, Gareth all missed
1 line of code causes it. Changing one sort comparator takes UNKNOWN from 52.9% to 5.2%. world-data.ts:529

The headline. Every accuracy number the project reports is measured with the correct character names handed in by the test harness. No user ever hands them in. The gap between "84% accurate" and what a writer experiences on day one is not a tuning problem, it is a plumbing problem, and it is cheap to fix.

02 — Current state

What actually exists today

The README describes eight subsystems. All eight are real and running. This is an unusually complete piece of software for a solo project, and the analysis is genuinely local, deterministic, and fast enough to run while typing.

The language engine

  • speech-detect.ts (116 KB) speaker attribution across four intelligence tiers, with cross-paragraph threading and dialogue alternation inference
  • chapter-analysis.ts (100 KB) tension, register, rhythm, pacing, sensory balance, scene labelling
  • world-data.ts (51 KB) entity extraction and classification into characters, places, factions
  • grammar-check, repetition, prose-profile, continuity, character-voice, chapter-dna, paragraph-risk, chapter-diff, local-review
  • prose-segments.ts shared tokenizer, apostrophe-safe quote analyser, discourse-marker taxonomy

What sits on top

  • 29 widget components feeding an Intelligence Panel
  • Adaptive layer that learns speaker attribution from writer corrections
  • Story graph and timeline accumulated per chapter after analysis settles
  • Renderer, a full Claude Code session bound to the project directory with eight slash commands
  • Export to TXT, Markdown, DOCX, EPUB and a six-preset typeset PDF
  • Liquid glass compositing layer, pixel-frozen and separately benchmarked

Note on the May market-readiness plan: it is now partly stale in the app's favour. Markdown, DOCX and EPUB export all exist in text-export.ts. Split view exists in preferences. Dark styling exists (68 prefers-color-scheme blocks) but there is still no in-app theme toggle, since nothing keys off a data-theme attribute.

03 — Accuracy, honestly

Why sixteen green suites do not mean the writer is served

The suites answer the question "does this function still behave the way it behaved when I wrote the test". They do not answer "does a novelist opening this app get correct answers". Those are different questions, and the second one had never been measured. So I built a harness to measure it.

The new harness

scripts/ood-language-audit.ts runs the real pipeline over two complete manuscripts and reports metrics that need no hand-labelling.

  • Hollow Iris, in-distribution. 22 of the 37 speech test cases were taken from this novel.
  • The Root Crown, genuinely held out. A different novel in a different register, mycopunk-gothic rather than political science fiction. No suite has ever been tuned against it.
  • Metrics. UNKNOWN rate, mean confidence, cast recall, and the rate at which the default and high modes name a different speaker for the same quote. That last one is an accuracy lower bound requiring no ground truth. If two modes disagree, one of them is wrong.
Finding 1 · root cause · confirmed

The name extractor ranks candidates by string length, then keeps the top 30

There are two entity extractors in world-data.ts, sitting forty lines apart. One is correct. The writer-facing path uses the other one.

// line 500 — autoExtractEntities, EXPORTED, feeds the World Data scan UI
  .sort((a, b) => candidateSortScore(b.n, b.idf, b.signals)
                - candidateSortScore(a.n, a.idf, a.signals))   ← relevance
  .slice(0, max)

// line 522 — autoExtractKnownNamesFast, private, feeds resolveKnownNames()
//            → speech detection AND the live highlight layer
  .sort((a, b) => b[0].length - a[0].length || b[1] - a[1])       ← STRING LENGTH
  .slice(0, max)   // max = 30

Sorting longest-first is correct for building the highlight regex, so that "Iris Vale" matches before "Iris". It is catastrophic as a ranking for truncation. A four-letter protagonist can never reach the top 30 of a list ordered by name length, because every novel contains thirty longer proper nouns. The sort-for-rendering is being used as a sort-for-selection.

Finding 3 · methodology

The suites are regression locks, not accuracy measurements

Fourteen of the sixteen suites report exactly 100% against targets of 85%. That pattern is not evidence of quality, it is the signature of tests written to describe the implementation's current behaviour. They are valuable, they will catch a regression tomorrow, but they cannot tell you whether the system is right.

Three of thirty-seven cases test prose outside the author's own voice, and those three were themselves written to be tested. Six cases test internal tuning parameters by name, which means the suite is partly measuring whether the implementation still has the shape it had when the tests were written.

This is not a criticism of the discipline, which is genuinely strong. It is a statement about what the discipline currently covers. The suites lock behaviour. Nothing measures generalisation, and the generalisation gap turned out to be enormous.

Finding 4 · the residual problem

Even after the fix, one attributed quote in six changes identity when the mode changes

The intelligence dial is presented as a speed and depth control. It is not. It changes the facts the app asserts. On held-out prose with the name list fixed, default and high name a different person for the same quote 16.4% of the time. Both cannot be right, and the writer has no way to know which reading they are looking at.

Bars scaled to a 20% axis. Fixing the names removes two thirds of the conflict on in-distribution prose and only a sixth of it on held-out prose, which is the real measure of how much of the engine's skill is tuned to one novel.

There is a second detail worth naming. In the shipped cold-start state, fast and default produce identical attribution on both manuscripts, 650 and 923 segments respectively, with identical UNKNOWN counts. When the name list is wrong, everything the default tier adds over the fast tier buys nothing at all. The user is choosing between two settings that do the same thing, and paying three times the latency for one of them.

Finding 5 · smaller, still real

Four more things worth knowing

  • Confidence policy has no owner. Eight different thresholds are hard-coded across eight modules: 0.50, 0.55, 0.58, 0.60, 0.65, 0.68, 0.70, 0.85. Nothing documents why they differ or what a change to one does to the others. The cold-start mean confidence of 0.35 sits below every single one of them, which is exactly why the failure cascades rather than degrading gracefully.
  • The LM enrichment pass changes nothing. test-event-labels reports 0 of 7 and 0 of 3 events relabelled. Whatever the narrative language model is contributing to story-graph event labels, it is not measurably improving them, while still costing a background pass.
  • The tension scanner reads vocabulary, not function. This is already documented and accepted, and the numbers hold it honestly at 88% on calm-versus-elevated. It cannot see dread carried by subtext rather than word choice, which is precisely the register a literary novelist works in most.
  • The semantic assist has a native dependency that can vanish. @xenova/transformers pulls sharp, which is currently unbuilt in this tree and takes two suites down with it. In a packaged Electron build that is a silent-degradation risk on the one path meant to improve entity classification.

04 — Real-world benefit

What actually helps a novelist, and what is decoration

The gimmick question deserves a direct answer, feature by feature. The test is simple. Would a working novelist change a sentence because of this, and would they have found the problem without it?

Renderer (Claude in the project)earns its keepThe strongest thing in the app. A persistent session with the manuscript's real files and a chapter-aware context packet is materially better than pasting into a chat window.
Repetition, grammar, prose profileearns its keepCatch things the eye slides over on the twentieth read. Deterministic, local, instant. This is what a writing tool should do.

The pattern. Everything that names a specific problem at a specific location earns its keep. Everything that reports a score without a target does not. The app currently produces far more measurement than judgement, and judgement is the thing a writer is short of at 11pm on chapter forty.

05 — UX problems

Six problems, in the order they hurt

  • 1. The app never says when it is unsure. This is the most damaging one, and it is a design problem rather than a code problem. A speaker attributed at confidence 0.35 renders with exactly the same visual authority as one at 0.95. A writer therefore learns, correctly, that the highlighting cannot be trusted, and then stops looking at all of it, including the 95% that was right.
  • 2. There is no cold-start moment. Import a manuscript and the app silently decides who the characters are, gets it wrong, and never asks. The single highest-leverage screen in the product does not exist.
  • 3. The intelligence dial exposes an implementation detail as a user choice. Fast, Default, High, Auto, Off. A novelist cannot possibly know which to pick, and as measured above, the choice silently changes who the app says is speaking.
  • 4. Twenty-nine widgets, two help affordances. Only CrossArcWidget and SensoryBalanceWidget mention help or explanation anywhere in their source, and five of twenty-nine have an empty state. A writer opens the panel, sees a wall, and closes it.
  • 5. The learning loop is behind an unmarked door. Annotation mode is the thing that makes attribution improve, and it appears in no onboarding page.
  • 6. The analysis lives in a different column from the prose. Writing is a single-column activity. Every glance sideways to a panel costs the sentence being held in the head.

Smaller and already known: no in-app theme toggle despite 68 dark-mode style blocks, preferences buried below the widget list, and no snapshot or checkpoint before a destructive rewrite, although chapter-diff.ts is written and tested and has no UI attached to it.

06 — What it should become

Seven changes, ordered by how much they change the product

The first four are the ones that turn this from an impressive engine into an app a novelist would refuse to give up.

01 · the breakthrough

Ink only what you are sure of

Stop rendering all attributions identically. Use the confidence number that already exists. Certain attributions get the full treatment. Likely ones get a lighter, unfilled treatment. Anything below the gate is not asserted at all, it is offered as a question the writer can answer in one keystroke.

Certain Nora "What's the governance bandwidth doing?" Likely Nora? "Since when?" Unsure who? "That's interesting." ← ⏎ to name

This single change does four things at once. It makes the system honest. It converts the 53% failure from an invisible defect into a visible invitation. It gives the adaptive learner the correction stream it was built for and never receives. And it earns back trust in the highlighting that was already correct, which is most of it.

02

Turn the cold start into the best moment in the product

After import, before anything else, show the cast the app believes it found and ask one question. Not a form. A list of faces with counts and a first line of dialogue each.

I found these people in your manuscript. Mira 412 mentions "I'll go with him." ✓ Gareth 288 mentions "The valley knows already." ✓ Tessa 193 mentions "Not before the loaves." ✓ Greythorn 87 mentions — a place, not a person ✗ [ Yes, that's my cast ]

Thirty seconds of the writer's time replaces an unsolvable inference problem with ground truth, and it is the moment the app proves it has actually read the book. Fix Finding 1 first so the list is right, then this screen is a delight rather than an apology.

03

Delete the intelligence dial. Converge instead.

Run the fast tier on every keystroke and the high tier when typing stops. Show the fast answer immediately, then let the deep answer replace it, and mark the few places where it changed its mind. The writer never picks a tier, and the 16% mode conflict stops being a hidden coin flip and becomes visible information, which is what it always was.

Keep Off. Off is a real preference. Fast, Default, High and Auto are the engine's vocabulary, not the writer's.

04

One margin rail instead of twenty-nine cards

Move analysis out of the panel and into the margin beside the line it is about, the way a copy editor's pencil marks sit next to the sentence. A repetition flag belongs next to the repeated word, not in a card three hundred pixels away that says "Repetition: 4".

The panel does not have to die. It becomes the place you go deliberately, and the default surface becomes the margin, which is where writers have accepted editorial marks for four hundred years.

05

One observation per chapter, not twenty-nine metrics

The system already computes everything needed to say something like "tension peaks at 73% and never releases, and this is the third chapter in a row that ends on the same beat". Say that. Put the twenty-nine widgets behind "show me everything". A number without a target is decoration, and a sentence with a location is an edit.

06

Attach a UI to chapter-diff, which is already built and tested

41 of 41 tests pass on a paragraph-level differ that nothing in the app surfaces. Two features fall straight out of it. Named snapshots before a rewrite, which is Scrivener's most-loved feature and the answer to the trust problem with destructive edits. And a revision view that says what changed since the last review pass and whether it addressed what was flagged.

07

Make the held-out harness a permanent gate

scripts/ood-language-audit.ts is now in the repo. Run it in CI alongside the curated suites and track UNKNOWN rate and mode conflict on a manuscript that nothing is tuned against. The curated suites answer "did I break it". This one answers "does it work for someone else", and that question had no owner before today.

07 — Architecture

Four places where the structure caused the bug

Framed as deepening opportunities, in the sense of more behaviour behind a smaller interface, with the change concentrated in one place.

1. Cast resolution has no owner

Two extractors with divergent ranking, and the private one feeds the writer-facing path. That is not a bug that happened, it is a bug the structure invited.

Deepen into one Cast module. It owns extraction, ranking, aliasing and provenance, so every name carries whether it was curated, inferred or confirmed by the writer. Two adapters already exist, so this is a real seam, not a hypothetical one.

Deletion test passes. Remove it and the divergence reappears across every caller.

2. Confidence policy is smeared across eight modules

Eight magic thresholds, no documentation of their relationship. You cannot reason about a change to one.

Deepen into a module that owns the bands, certain, likely and guess, and the policy for what each band is allowed to assert. The interface becomes the test surface, so you can finally test what the writer sees rather than what number came out.

Idea 01 above is not implementable cleanly until this exists.

3. Tier policy is interleaved through the detector

speech-detect.ts is 116 KB with level === 'high' guards threaded through it. Adding a tier means editing the detector, and the detector cannot be tested independently of tier policy.

Deepen into a level-agnostic detector plus a policy module that composes passes. Idea 03, converging rather than choosing, becomes a policy change instead of surgery.

4. The evaluation seam is missing

Every suite shares one shape, curated cases with hand-supplied names, so every suite shares one blind spot. Nothing could have caught Finding 1, because every test hands in the answer the extractor was supposed to produce.

Deepen into a second suite shape, whole-manuscript and label-free. That harness now exists. Making it a gate closes the blind spot permanently.
